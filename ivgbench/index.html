IVG-Bench

A visual interaction model watches a simulated user carry out a physical task and can change the outcome only by talking. Each episode pairs a task in one of three simulators (cooking, household, phone settings) with a user persona and a hidden schedule of out-of-plan events: execution errors, questions, proactive requests and plan changes. The user reacts to what the model says, and scoring reads the simulator's own record instead of reference responses.

Statistics

  • 105 cases in three simulators, each run with three user personas: 315 episodes per model and run. A case fixes the task, the starting state and a hidden schedule of events; everything after that happens live between the simulated user and the model.
  • 371 scheduled events, 2 to 7 per case. Questions, proactive requests and plan changes exist only in CookSim; VH-Home and ScreenSim schedule mistakes only.

Construction

Figure 1. From a benchmark case to a scored closed-loop rollout
Paper: Sec. 3, Sec. 4.1

The benchmark runs in three steps: define an episode, roll it out in closed loop, score the record. The five boxes are the five modules, and each has its own figure below.

The loop has two channels. Actions pass only between the user harness and the world engine: the user acts, and the engine returns structured state and execution feedback. Language passes only between the user and the assistant. The single line from the engine to the assistant carries rendered frames in one direction, so the assistant can change the outcome of a task only by persuading the user.

Figure 2. One episode: the case, the persona, and what the assistant is told
Paper: Sec. 3.2, Sec. 4.1, App. G.1, App. G.4, Tab. 1, Tab. 17, Tab. 18

An episode is one case paired with one persona. The case fixes the task, the initial scene and the event schedule; the 50 CookSim cases, for instance, are five recipes in two kitchen layouts with five schedules each. Every case is run with three personas, which turns 105 cases into 315 episodes.

Colour marks what the assistant is told. It knows the task and the two preferences the user states up front: execution speed and how often to be interrupted. The event schedule and the skill and trust levels stay hidden, and the assistant has to read them from behaviour. Each scheduled event names a progress trigger, its target objects, the action or utterance to produce, and the condition that ends it.

Figure 3. What is written before a run, and when the scheduled events fire during it
Paper: Sec. 3.2, App. G.4, App. K.3

Two things are fixed before a run and written into the case file: the task goal, split into the sub-goals the progress tracker checks, and an event schedule designed separately from it. The schedule is hidden from the assistant. The Fish and chips case of the running example carries seven events: three execution errors, two questions, one proactive request and one plan change.

During the rollout the events fire in task order rather than at fixed times. Each is attached to a progress trigger, a condition on the scene graph such as a sub-goal being reached, so the tick at which it fires depends on how fast the user works. The ticks on the timeline are those of the recorded episode in Appendix K.3: the raw fish is plated at tick 27, the forgotten step is triggered and prevented at tick 39, the user asks whether anything is done at tick 78, asks to be told when the potato is ready at tick 113, announces the lettuce at tick 192, and the episode completes in 215 ticks. Between events the simulated user simply works through its plan, and the assistant is never told that an event has begun or ended.

Figure 4. How one semantic action becomes a state change and three outputs
Paper: Sec. 3.1, App. G.2, App. G.3

The engine processes one semantic action per tick. Users issue commands at the level people speak; an LLM grounding module resolves the references to simulator objects, and the engine expands the command into low-level controls and updates the scene graph. An action whose reference cannot be resolved, or whose precondition fails, is rejected with feedback.

The update leaves the engine in three forms. The user receives structured state and feedback, the assistant receives only rendered frames, and the progress tracker checks sub-goal conditions on the graph. The tracker's result triggers scheduled events (Figure 5) and decides task completion at the end (Figure 7). In the example one scoop puts raw fish on the plate: the user side is told so in text, the tracker finds the cooked-fish sub-goal unmet, and the assistant gets a picture of the plate.

Figure 5. The simulated user: a planning VLM plus a scheduler that can intervene
Paper: Sec. 3.2, App. J.1, App. J.2, App. J.5

Outside scheduled events only the part below the dashed box runs. On each turn the harness assembles a prompt from the persona, the user's private state (state map, remaining action queue, feedback on its last action) and the dialogue. The user VLM returns an utterance, which may be empty, a conversational move, and an update to its action queue. Only the utterance reaches the assistant; the queue releases one action per tick to the engine.

When the progress tracker reports that a trigger condition holds, the event scheduler does two things at once. It overrides the action queue, so the scheduled error really happens, and it injects a private instruction that tells the VLM which mistake is under way and forbids revealing or repairing it. From then on the VLM controls only what the user says, until it judges the assistant's diagnosis correct and answers with an accept move, or the event completes or times out. Questions, proactive requests and plan changes need no forced action and use the instruction path alone.

Figure 6. What the evaluated model receives on each query, and what leaves it
Paper: Sec. 4.1.1, App. H, App. J.4

The figure shows the setting for non-streaming models in CookSim and VHSim. The model is queried every two ticks with the eight most recent frames, the task and the user's stated preferences, the dialogue, and the progress notes it wrote on the previous query. It never sees the structured state, the event schedule or the user's private plan. Streaming models keep context inside their session and need neither the window nor the notes.

Of the three outputs only the text reaches the user, and it arrives late. The main results fix the delay at two ticks; the latency ablation converts measured inference time at about 1.2 seconds per tick, so a six-second reply lands five ticks later. The error flag is read by scoring and does not change the task by itself. The progress notes return as recurrent memory, so the model's picture of task progress is built from what it saw and is never corrected by the engine.

Figure 7. Which part of the execution record each metric reads
Paper: Sec. 3.3, App. D, App. E, App. I

Every metric is computed from the engine's record of the rollout; no reference response is involved. Each row pairs a piece of evidence with the metric that reads it.

In the second row the event log holds a forgotten-step event at tick 39 and a warning that arrived in time, so the error counts as both detected and prevented. In the third row the assistant says both potato portions are on the plate while the engine state holds one; that is a false factual claim, and the factual-grounding gate sets the round's interaction quality to zero.

Evaluation

In-time success
Share of episodes whose goal, verified by the engine on the final state, is met within the completion budget. \(T_i^{\mathrm{ref}}\) is the length of an engine-generated error-free rollout and \(\alpha_i\) the allowance for scheduled events (case-specific in CookSim, 20 ticks in VH-Home); ScreenSim uses \(2T_i^{\mathrm{ref}}+8\).
\[S_i=\mathbb{1}\big[\,G_i(s_i^{\mathrm{final}})=1\ \wedge\ T_i\le 2\,(T_i^{\mathrm{ref}}+\alpha_i)\,\big]\]
Detection recall
Share of triggered errors identified inside their detection window, either by an event flag the engine accepts or by a diagnosis the simulated user judges correct. Events whose trigger is never reached are left out.
\[R=\frac{\sum_i N_i^{\mathrm{detected}}}{\sum_i N_i^{\mathrm{triggered}}}\]
Error prevention
Share of triggered errors stopped before the point of no return, which also requires the user to accept the guidance and change course. Reported in the latency comparison.
\[P_{\mathrm{prevent}}=\frac{\sum_i N_i^{\mathrm{prevented}}}{\sum_i N_i^{\mathrm{triggered}}}\]
Interaction quality
Each assistant reply, together with what the user then said and did, is judged against the simulator state by two LLM judges on binary rubric items in five categories: factual grounding, situational relevance, actionable guidance, user intent uptake, guidance conciseness. A category passes when all of its applicable items pass (\(q_{rjc}\)); the score of judge \(j\) for round \(r\) is the mean over its applicable categories \(C_{rj}\), set to zero by the gate \(g_{rj}\) if factual grounding fails; the judges are then averaged.
\[Q_{rj}=g_{rj}\,\frac{1}{|C_{rj}|}\sum_{c\in C_{rj}} q_{rjc},\qquad Q_r=\frac{1}{|J_r|}\sum_{j\in J_r} Q_{rj}\]
Question answering
CookSim only. Reference facts come from the recorded state transitions, and a semantic judge gives 1, 0.5 or 0 per answer.
Proactive requests
CookSim only. Credit requires a readiness notice inside the window derived from the state, with no premature alert; acknowledging the request is not enough.
Reply delay
In CookSim and VH-Home the main results deliver each reply two ticks after the observation it was generated from; ScreenSim replies arrive without delay. The latency comparison converts measured inference time into ticks at 1.2 s per tick, during which the user keeps acting.
